语音识别不买 GPU 行不行？先看懂 CPU 的四笔账

2026-06-22 发布 · 2026-11-22 修订 · 部署选型科普

你有一台普通电脑，想把十分钟的采访变成文字。看到一个语音模型只有几百 MB，第一反应可能是：“这么小，我的电脑应该能跑吧？”文件能装进硬盘，只回答了最容易的那个问题。模型运行时还需要内存和计算；识别得快不快，还取决于录音、运行方式，以及你能等多久。

这篇不推荐你先买硬件，也不让你先照抄一串安装命令。读完后，你可以为一个具体转写任务写出验收条件，知道哪些数字需要测、怎样比较，避免因为“支持 CPU”就误判它适合自己的应用。本文是选型与测量概念指南，不需要安装软件；所有计时例子均为虚构，不是产品性能数据。

1. 先说清楚：你要跑的是模型，还是完整应用？

语音识别（ASR）是把声音变成文字的任务。模型权重是训练得到的数值文件，像一份学会了识别规律的“参数表”；它不能自己执行。运行时负责加载这些参数并完成计算。服务在运行时外面增加接收请求、排队、返回结果等功能。它们不是同一件东西。

在 FunASR 生态中，FunASR 是工具包，可以组织模型调用和前后处理；Fun-ASR、SenseVoice 是模型系列，能力取决于具体 checkpoint（某个版本的模型权重）；FunClip 是转写与剪辑应用。安装了工具包，不等于已经下载了权重；模型能识别文字，也不等于现成支持你需要的字幕时间、说话人或 HTTP 接口。

对初学者，先用 Python 转写入门完成一段录音，比同时研究量化、服务器和编译更容易判断问题在哪里。如果目标机器不适合安装 Python 推理环境，可以再评估独立的 C++ / GGUF 路径。GGUF 是模型文件格式，不是把任意模型文件改个后缀就能使用。官方的 llama.cpp / GGUF 运行时说明列出了对应模型和可执行程序。

“推理时不需要 Python”也有范围：它指相应的独立 C++ 程序，不涵盖所有下载、转换和服务工具。例如这份文档中的下载助手使用 Hugging Face CLI，HTTP 包装服务使用 Python。选择安装包时，还要匹配操作系统、CPU 架构和该构建的指令集要求。x64 与 ARM64 不是可互换的文件；某台电脑能运行，不证明另一种 CPU 已经受过验证。

先确定产物：这次只要一份最终文字，还是边说边出现字幕？是否还要时间戳、标点或说话人标签？本文以“本地录音转成最终文字”为主。独立 GGUF 程序的 VAD 可以切分语音，但该文档明确说明它不实现 CAM++ 说话人向量与聚类，不能把这条路径等同于完整的会议分析管线。

2. 第一笔账：硬盘放得下，不代表内存够用

下载页上的 MB 通常描述文件大小。运行后，程序还会保存中间计算结果、音频数据和其他状态；额外的 VAD、标点或说话人模型也可能占用内存。因此，要分别记录权重占用的磁盘空间和运行时的峰值内存。不要拿其中一个代替另一个。

量化可以理解成用更紧凑的数值表示部分权重：文件可能变小，某些硬件和实现上的计算也可能受益，但效果取决于具体模型、量化方式和运行时。它不是“无损压缩”的同义词。更小的文件不能证明准确率不变，更不能保证所有 CPU 上都更快。比较量化版本时，必须用同一组录音检查文字是否仍满足任务要求。

对于一个单进程程序，可以关注峰值 RSS，即操作系统统计的该进程驻留物理内存峰值。服务如果还启动了工作进程或子进程，只看主进程就可能漏算；逐进程 RSS 简单相加又可能重复计算共享页。比较前要固定测量范围，例如“单个推理进程”或“同一容器的总内存”，并记录口径。

当电脑开始频繁把内存内容换到磁盘，程序也许没有立刻报错，却可能明显变慢。应为系统和其他应用留下余量，再用计划处理的最长录音、实际批量和工作进程数检查，而不是凭一条短音频成功就认定容量足够。

3. 第二笔账：RTF 告诉你处理速度，不直接告诉你用户等多久

实时率 RTF（real-time factor）= 处理耗时 ÷ 音频时长。分子和分母都用秒，结果没有单位。比如十分钟音频是 600 秒，处理用了 120 秒，RTF 就是 0.2。数字越小，表示在这个测量范围内完成同样时长音频所需时间越短。RTF 小于 1，只说明处理比音频播放快。

下面三个例子都是虚构的算术示例，不是三款模型的对比，也不是对你的电脑的预测。这里约定“处理耗时”包含音频预处理、识别和文本后处理，但不包含模型加载、网络传输与排队。

情形音频时长处理耗时RTF
已加载的程序处理采访600 秒120 秒0.2
另一次不同条件的处理600 秒360 秒0.6
短录音处理10 秒2 秒0.2

再假设第一种情形必须先加载模型，加载用 45 秒，那么从启动到拿到文字至少是 45 + 120 = 165 秒，还没计入其他开销。第三种情形虽然同样是 RTF 0.2，用户如果也要等这 45 秒加载，就不会觉得“两秒就出结果”。长驻进程可以复用已加载的模型，但要另算持续占用的内存。

这就是冷启动与热运行要分开的原因。第一次下载权重的等待应单独记录；下载完成后第一次启动并加载模型是另一项；模型已加载后的后续请求又是一项。不同缓存、硬盘和运行时会改变这些时间，不能把三者混在一个“耗时”里，也不要只挑最快的一次。

工具日志里的 RTF 还可能采用不同的计时起止点。在本文引用的 AutoModel 源码中，RTF 由计时累计量与对应音频时长计算；它不是浏览器或客户端从发起请求到收到结果的计时器。因此服务评估还要单独记录请求延迟，包含你实际关心的上传、排队和返回过程。

离线识别不等于断网运行。在语音任务中，“离线”常表示拿到一段完整音频后再处理，与流式相对。要断网使用，还需预先备齐兼容的软件依赖、全部模型权重和配置，并确认调用路径不会在线查找或补下载。缓存存在只是条件之一，不是任意调用都无需联网的保证。

4. 第三笔账：一条录音够快，不等于多用户够快

把采访一次处理完，只需要最终结果；实时字幕则还需要在录音尚未结束时持续给出片段。这要求模型与调用路径支持相应的流式协议，并考虑音频分块、首字等待、句末判定和结果修订。把文件识别改成每隔几秒调用一次，并不能自动得到连续、稳定的实时字幕。RTF 小于 1 也不能替代这些要求。

线程数是一个进程内部并行工作的配置；并发数是同时处理多少个请求。二者不是同一个旋钮。更多线程不一定更快，多个进程还可能争抢相同的 CPU 与内存带宽。官方 AutoModel 的 ncpu 会影响进程内线程设置；不是为每个请求独占预留相应数量的 CPU。不要在每个请求中随意改它，再把变化误认为模型波动。

部署服务时，先测一个请求，再测你真正需要的并发数，记录排队后的延迟与失败数。单条录音 RTF 0.2 不能直接推出“五个请求同时运行也够快”。若报告 p95 延迟，要解释它是测得请求中约 95% 不超过的延迟，并同时写明样本数、并发和计时范围；几次请求不足以支撑稳定的尾延迟结论。

5. 第四笔账：识别是否可用，和跑得快一样重要

先把“够用”写成一句可检验的话。例如：“对我有权使用的十分钟中文采访，启动后五分钟内拿到可编辑文字；关键人名和数字由我复核；处理时不能让这台办公电脑失去响应。”这是示例需求，不是产品承诺。你的时限、质量标准和内存预算应由用途决定。

  1. 固定输入和版本。用自己获授权的录音，或公开来源中许可明确、可合法使用的样本；保留输入哈希、时长、语言、噪声与是否重叠说话的说明。记录准确的模型标识与 revision、运行时版本、操作系统、CPU 型号与架构。本文不提供需读者猜来源的音频文件。
  2. 先完成一条完整链路。拿到真实输出，确认它包含任务需要的文字或字段，再讨论优化。人工回听重点片段，尤其是人名、数字、否定词；空结果、漏段和失败也要保留，不能只比较成功样本。
  3. 分开记录冷、热与并发条件。下载、首次加载、已加载请求分别计时。固定线程数和音频处理选项，做多次重复，保留每次结果以及机器上其他负载。再增加目标并发或录音长度，一次只改变一个条件。
  4. 按任务决定下一步。若质量不达标，先检查录音、语言与模型路径是否合适；换 GPU 不会自动解决选错模型的问题。若质量合格但耗时或内存超预算，再评估线程、批量、分段、量化或其他硬件，每次都复查质量。批量归档可以接受的等待，未必适合互动对话。

最低限度，你最终应该有一张记录表：哪段录音、什么版本、什么机器、什么运行条件、耗时多少、占用多少、文字是否通过复核。它比一句脱离环境的“CPU 很快”更能帮助你做采购或部署决定。模型和依赖的使用许可也应逐项核对，不由文件大小或“开源”两个字推断。

6. 给 Agent：保存可比较的记录，不自动扩大操作范围

以下是建议的应用侧评估记录，不是 FunASR SDK 保证返回的字段。先取得用户任务、数据与下载授权，再填写环境和测量值；不要自动购买计算资源或把录音上传到远程服务。

  • 来源：input_path 为用户指定的本地文件绝对路径字符串，不是示例占位文本；另存输入 SHA-256。model_id、model_revision、runtime_version 为确切标识字符串；同时记录 OS、CPU 型号、架构、Python 与依赖版本（非 Python 路径注明不适用），不能只填“最新版”。
  • 条件：threads 和 concurrency 为正整数，分别表示实际线程配置和同时请求数。warm_state 用字符串 cold 或 warm，并另存模型是否已加载及缓存状态的说明。软件安装与权重下载是不同操作；新下载、数据上传、付费资源和覆盖原文件均需相应授权。
  • 计时：audio_duration_s 为有限正数；processing_s 与 request_latency_s 为有限非负数，单位均为秒。记录各自起止点。只有完整成功且口径一致的处理才能计算 processing_s / audio_duration_s；时长未知或为零时不生成 RTF。
  • 内存与结果：peak_rss_bytes 为非负整数字节数，并明确进程范围；未测量写 null，不填 0 冒充测量。保存原始转写、人工复核状态及 status（ok 或 error）。失败项保留 error 原因和已完成范围，不能当作零耗时成功。
  • 失败与退出：依赖缺失、模型/运行时不匹配、指令集不兼容、内存不足或无数据授权时停止，返回错误状态；批处理命令应返回非零退出码并保留失败列表。不得自动重试这些确定性错误。仅明确的暂时性故障才按用户事先允许的次数重试，记录每次尝试；参数改变后的测试属于新条件，不能覆盖原记录。

例如遇到 Illegal instruction，先核对 CPU 架构、指令集和二进制构建要求，不要反复重启同一程序；内存不足时先确认范围与并发，不要直接启动更多进程。下载失败不能通过换用未授权的镜像、账户或上传渠道“自动解决”。
