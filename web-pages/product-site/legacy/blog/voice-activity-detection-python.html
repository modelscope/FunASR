VAD 找到语音以后，为什么还不能直接做字幕？

2026-06-22 发布 · 2026-11-20 修订 · 语音技术入门

一段会议录音，前面有人调麦，中间有长停顿，后面才开始讨论。你希望程序先找到值得转写的部分。VAD 就像给录音画出“这里可能有人说话”的标记：它能帮助定位语音，却没有听写文字，也没有替你剪掉任何声音。

读完这篇，你应能看懂一组语音起止区间，知道它与裁剪后的音频、字幕时间戳分别是什么，并判断自己的应用还缺哪一步。本文是概念指南，不需要安装软件；下方数字是人为构造的示意，不是模型推理结果。

1. 三个问题，不是同一个模型能力

VAD（Voice Activity Detection，语音活动检测）判断音频中的哪些时间区间可能包含语音。ASR（Automatic Speech Recognition，自动语音识别）回答“说了什么”。若要字幕，还需要把文字与时间关联；若要区分发言者，还需要说话人处理。VAD 本身不输出字词，也不判断是谁在说话。两个人无缝接话，完全可能仍在同一个语音区间里。

在这个生态中，FunASR 是工具包，可以调用 VAD、识别等组件；Fun-ASR 和 SenseVoice 是模型系列，具体 checkpoint 的能力要分别核对；FunClip 是转写、字幕与剪辑应用。本文聚焦 FunASR 中的 FSMN-VAD 文件处理结果，不把其他模型、HTTP 服务或 GGUF 运行时的返回格式当成同一接口。项目职责可查阅官方仓库说明。

如果目标只是先获得文字，从第一段录音转写教程开始更合适；需要挑选字幕或剪辑后端，先看按产物选模型。不要为了“流程看起来完整”就叠加一套 VAD：已有管线可能已经完成分段，重复切分还可能改变上下文与时间轴。

2. 看懂区间：标记不是剪刀

FunASR 的 FSMN-VAD 文件路径返回记录中的 value 存放语音区间，形如 [[start_ms, end_ms], ...]。start_ms 和 end_ms 是这里对每一对数值的说明，不是另两个返回字段；单位是毫秒，参考点是送入此次处理的音频起点。源码分别实现了区间生成和推理返回。

假设原录音长 10 秒，示意区间为 [[1000, 3000], [6000, 9000]]。这是为了讲解而编造的数字，不是某个音频或模型的实测输出。

区间（毫秒）原录音位置（秒）区间时长
[1000, 3000]1.0 到 3.02.0 秒
[6000, 9000]6.0 到 9.03.0 秒

换算方法是除以 1000：6000 毫秒就是 6 秒；第二段时长为 (9000 − 6000) / 1000 = 3 秒。这张表只告诉你“模型将哪里标成语音”。原文件仍长 10 秒，并没有因此变成 5 秒。只有后续程序真的读取这些片段、拼接并写出新文件，音频才被剪辑。

未被标记的部分也不能直接叫“纯静音”：它可能有背景声，也可能是漏检的轻声。VAD 是预测，不能据此断言原录音里没有重要内容。保留原文件，先回听边界附近，尤其是轻声开头、句尾和背景音乐下的人声。

3. 裁剪以后，时间从哪里开始算？

假如把第二个区间单独保存成一个 3 秒片段，这个新文件从 0 秒开始。但它对应的是原录音的 6 秒处。若下游支持时间戳，并在片段内给出某个词的时间 [0.4, 0.9] 秒，把它放回原录音时应得到 [6.4, 6.9] 秒。

映射关系：原录音时间 = 片段内时间 + 片段在原录音中的起点。这个示意假定没有变速或其他时间拉伸，且片段起点确实是 6 秒。如果裁剪时多留了前后余量，就记录实际裁剪起点，而不是照抄最初的 VAD 起点。

如果把两个区间首尾拼起来，第二段在拼接文件里从 2 秒开始，在原录音里却从 6 秒开始。此时整份文件不能共用一个固定偏移。应为每一段保存“原文件位置 → 新文件位置”的映射，且不能把跨拼接点的时间戳当成原文件中的连续声音。

对会议字幕或证据回溯，通常先保留原录音和分段映射更稳妥；对只需听取摘录的应用，去掉停顿也可能合理。两种产物没有谁天然更好，关键是明确字幕或检索结果要指向哪条时间轴。

4. 有了 VAD 时间，为什么还不够？

一段 3 秒语音可能包含一句话、半句话，也可能有多个人交叠发言。VAD 区间不是语义句子，更不是每个字的对齐位置。把整段文字平均分到每个字上，只是人为分配时间，不能声称是模型的字级时间戳。

  • 做可搜索文字：把符合接口要求的音频交给识别模型，再检查转写内容是否忠实于录音。
  • 做视频字幕：选择明确支持所需时间戳的模型与接口；保留时间轴映射，再进行字幕分行、时长和同步检查。VAD 可以协助分段，不能替代文字对齐。
  • 按发言者检索：增加合适的说话人处理。匿名标签只用于区分录音内的发言者，不等于实名身份。

是否省时、是否减少错误，需要在同一批有代表性的音频上比较完整流程。漏掉的语音无法靠后面的识别模型凭空恢复；切得过碎也可能损失上下文。本文不据一次示例承诺实时性、识别提升或费用下降。

5. 文件结果与流式事件不能混用

上面的解释针对完整文件处理后的闭合区间。流式处理是声音不断送入的过程，程序可能先知道“开始说话”，稍后才知道“结束”。对应实现可能返回 [start, -1]、[-1, end]、完整区间或空列表。这里的 -1 是端点尚未在该事件中提供的标记，不是负一毫秒的裁剪位置。

需要流式应用时，应按专门的流式 VAD 文档处理缓存、分块和结束信号，不把本文的区间示意作为流式客户端协议。

给 AI Agent：先保护时间轴，再决定处理动作

以下是应用侧验收约定，不是可直接传给 SDK 的配置对象。本文没有执行命令；接入时须核对所用版本的实际参数和错误行为。

  • 输入：记录用户授权的真实音频路径、时长（秒）、采样率（Hz）、声道数，以及模型 ID、revision 和运行时版本。不能根据后缀猜音频格式，不能把重命名当成重采样。
  • 输出：为完整文件的 value 检查二维数值列表和毫秒单位。裁剪前确认端点有限、顺序合理、0 ≤ start < end 且不超出实际输入时长。零长度、越界或未闭合区间应保留原结果并进入核查，不静默改值后宣称模型正确。
  • 空结果：一次成功处理返回 [] 表示没有输出语音区间，不是网络错误，也不是“文件一定没有语音”的证明。保留原音频并检查输入与检测条件，不无限重试。
  • 失败边界：程序异常或非零退出与“没有检测到语音”分开记录；修正原因后才按约定有界重试。不要自动换模型、上传音频或把旧结果冒充本次结果。
  • 操作权限：安装工具包与下载权重是两件事；首次加载可能下载额外文件。断网运行要先备齐并验证依赖、权重和配置。下载、外部上传、付费接口、覆盖或删除音频都需相应授权，模型许可不能从工具包许可推断。

读到这里，你能回答这三个问题吗？

  1. 示意区间总长 5 秒，原录音变短了吗？没有，返回标记不等于写出剪辑文件。
  2. 第二段内 0.4 秒的位置，在原录音哪里？6.4 秒，前提是片段从原录音 6 秒处开始且没有变速。
  3. 一个 VAD 区间意味着一句话或一个说话人吗？都不意味着。
