实时字幕为什么会改字？读懂流式识别的三种状态

2026-06-17 发布 · 2026-11-24 修订 · 语音技术科普

开会时，屏幕先打出“我们周四见”，说话人停顿后，字幕又变成“我们周五见。”这不一定是播放器出错：有些系统先用正在到达的声音给出临时结果，再用一整段声音重新识别。但如果接入程序把两次结果都追加到正文，你会看到同一句话出现两遍；如果它把第一句的“完成”当作整场会议结束，后半段就可能丢失。

本文回答一个问题：一条实时识别消息来了，应该追加、替换，还是结束任务？读完后，你能为字幕应用划分“当前草稿、已完成片段、整份输入”三层状态。它是原理解读，不是服务器部署教程，无需安装软件。文中对话和消息顺序是虚构示例，不是模型实测结果。

阅读导航：先选对路径 · 流式怎样工作 · 读懂消息 · 延迟从哪来 · 怎样验收 · Agent 接入约定

先确认：你需要边说边出字，还是录完后交付？

FunASR 是工具包，用于组织模型调用和处理流程；Fun-ASR、SenseVoice 是模型系列，具体能力取决于选用的模型、权重和运行方式；FunClip 是转写与剪辑应用。本文讲的是 FunASR 中的流式 Paraformer，以及官方仓库的 Python WebSocket 示例。不能因为这些项目都能处理语音，就把离线模型换一个名字当作流式模型，或认为剪辑应用天然提供实时字幕服务。

如果目标只是把已有录音整理成文稿，先完成第一段录音转写，通常不必同时处理网络会话、临时文字和修订。如果观众必须在说话过程中看到文字，才需要考虑流式路径。2-pass 是“两遍处理”：第一遍尽早反馈，第二遍在片段结束后重新识别。它适合允许字幕修订的体验，不适合把每一个临时字立即作为不可撤销的付款、发信或设备控制指令。

安装包是程序，模型权重是程序加载的参数文件，运行时负责执行，对外服务还要管理连接、鉴权和资源。只安装 funasr 不等于已备齐所有模型，更不等于部署好了服务。下面的协议说明只针对引用的 Python 示例源码；C++ 服务、HTTP API 或其他模型应另核对各自契约。更多取舍见模型与运行路径选型。

流式不是把录音随便切小，再各认各的

离线识别可以先拿到一个完整输入。流式识别则要在声音尚未到齐时分块处理：前一块留下的状态，帮助模型理解后一块。这份跨块状态通常称为 cache（缓存）。这里的缓存不是硬盘上的模型下载缓存，而是当前音频会话的推理状态。

在本文核对的流式 Paraformer Python 路径中，连续音频块复用同一个缓存；最后一次调用用 is_final=True 请求收尾。每块都换成一个空字典，相当于反复让模型从头开始；不同录音共用一份缓存，又可能串入不相干的上下文。一个块没有返回文字也不等于失败：当前声音未必足以形成可输出的文本。最后不足整块的声音仍需按接口要求收尾，不能直接丢弃。

另一层是 VAD（语音活动检测），判断哪里像有人说话、哪里可能结束了一个语音片段。它不是语法分析器：一次停顿不保证恰好是一句话，数字、专名或长句也可能跨过停顿。2-pass 的第二遍拿到更多片段上下文后，可能改词、补标点，也可能仍然识别错误。“第二遍”描述流程，不是准确率保证。

把草稿、片段终稿和输入完成分开

先理解两种不同的文字接口。增量输出每次给一部分新文字，例如先来“我们”，再来“周四见”；显示层可以把它们连起来。累积假设每次给当前整段，例如先来“我们”，再来“我们周四见”；若照样追加，就会变成“我们我们周四见”。不能凭“流式”两个字判断是哪一种。

最后一行之前，文件输入客户端会发送 is_speaking=false 和 is_end=true，服务端处理尚未结束的在线、离线工作后回复确认。若收尾记录了错误，确认中的 is_final 为 false，并带 error。收到一条片段结果、发送完最后一帧、连接被关闭，这三件事都不能替代成功的结束确认。

还要防止另一个误解：成功确认不保证一定有非空文字，更不证明转写正确、标点正确或所有附加功能都成功。本文引用的服务实现对某些辅助处理错误有单独处理路径。应用应分别检查协议完成、所需字段和实际内容，不用一个布尔值包办质量验收。

示例客户端的显示逻辑也不是通用的并发修订协议。不要假设返回对象总有可用的片段 ID 或重放去重 ID。对接前须确认消息顺序和片段归属；应用自行维护的连接标识、片段编号与修订记录，应与原始服务字段分开。无法确定一条修订属于哪段时，停止自动拼接并保留原消息，不靠文字相似度偷偷覆盖历史。

600 毫秒的音频块，不等于 600 毫秒看见字幕

官方流式示例使用 chunk_size=[0,10,5]，中心块的示例输入步长是 10 × 960 = 9600 个采样点。在 16000 Hz 下，这批声音覆盖 9600 / 16000 = 0.6 秒。这个除法算的是音频时长，不是一次推理的耗时，也不是说话开始到屏幕出字的实测延迟。

观众感受到的等待还包括音频积累、模型所需上下文、上传与排队、计算、结果传输和页面刷新。第二遍结果还可能要等 VAD 判定片段结束，再完成离线识别。所以至少要分别观察：首次可见文字有多快、文字还会修订多久、说话结束后多久出现片段终稿。把音频快速读入内存后测得的吞吐，不能直接作为麦克风场景的响应速度。

块更小不保证所有等待都缩短。固定开销、调度与并发可能影响总效果，参数也必须符合所用模型的约定。CPU 能否满足目标，取决于具体模型、音频、机器、线程和并发负载；GPU 同样不保证端到端实时。本文没有测量或承诺任一设备的实时性能。

做字幕前，先验收这四个场景

  1. 有修订的两段话。保留原始消息，检查第二遍替换的是当前片段，而不是追加出重复句，也不是抹掉前一段已经完成的内容。
  2. 结尾很短、几乎没有停顿。检查最后不足整块的声音有没有送完，结束确认之前有没有遗漏尾词。不要通过截掉录音结尾来让流程“成功”。
  3. 静音或没有可识别内容。允许无文字结果；把“协议正常结束但无文字”与“超时或推理失败”区分开，不编造字幕填空。
  4. 断网、超时和服务端报错。把任务记为失败或不完整，并保留已收到的片段。不能因为草稿区已有字，就把整份录音标成成功。

这些检查需要你在自己的环境里，用有权处理的音频实际完成；本篇没有替你运行它们。字幕验收还要回听人名、数字和否定词。对语音助手来说，临时转写可以用于可撤销的界面反馈，但涉及发信、付费、删除等动作，应等待应用规定的确认，不能把 ASR 的“final”当作用户授权。

给 Agent：先保存事件，再生成字幕

针对本文引用的 Python WebSocket 路径，记录精确源码提交、模型标识和配置。下列字段不是整个 FunASR 生态的统一接口；对接其他服务时必须重新核对。

  • mode 是字符串。请求可选 online、offline、2pass；两遍结果可能用 2pass-online / 2pass-offline。按消息类型处理，不能只检查是否存在 text。
  • text 是识别字符串，可能为空；结束确认可以没有这个字段。is_final 与 is_end 是布尔值，分别结合片段结果和结束确认理解，不能互换。wav_name 是输入名称字符串，不是已验证的身份、路径或唯一去重键。
  • 应用侧另存连接标识、接收顺序、原始消息和派生字幕版本。默认按单连接、有序处理的已确认契约设计，不把多条录音的缓存或草稿混在一起；这些应用侧字段不要伪装成服务端已经返回的字段。
  • 文件输入结束后，有界等待匹配的结束确认。示例 CLI 的 --result_timeout 单位是秒，默认 300；它是等待上限，不是性能保证。超时、负向确认或提前断连必须报告不完整。协议错误不自动重试；临时网络失败也只能在已授权次数内重试，并将新尝试分开记录，避免重放重复字幕。
  • 阅读本篇无需下载模型或上传录音。真正接入前，需分别确认软件依赖、模型权重及许可、首次下载权限和部署环境；后续离线使用要备齐文件并验证不会补下载。麦克风采集、音频上传、付费服务与保存他人录音需要相应授权，不能由“测试实时字幕”自动推导。

出现重复字，先核对增量还是累积假设；出现重复句，先核对离线修订是否被再次追加；缺结尾，先核对尾块和结束确认；延迟很大，分开测量排队、推理与端点等待。先找出是哪一层出了问题，再决定改模型还是改接入代码。
